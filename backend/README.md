# Чтиво · Магазин — backend (MVP)

FastAPI-бэкенд первой итерации: каталог товаров, все рассматриваемые способы
доставки, заказы и оплата-заглушка. Веб-админка (SQLAdmin) даёт добавлять и
редактировать товары и способы доставки без правки кода.

## Что уже есть

- **Товары** (`app/models.py:Product`) — номер / подписка / мерч, цена, остаток,
  признак активности. CRUD — через админку `/admin`. Обложку можно либо
  загрузить файлом прямо в форме товара (поле «Image Upload» —
  `app/media.py`, хранится на диске процесса и отдаётся статикой по
  `/media/...`), либо вписать внешнюю ссылку в `Cover Url` вручную — при
  загрузке файла его публичный URL сам подставляется в `Cover Url`, который
  и читает Mini App. На хостинге с эфемерным диском (например, Render на
  бесплатном плане) загруженные файлы не переживут рестарт/редеплой — для
  реального продакшена заменить `FileSystemStorage` на `S3Storage` (тот же
  интерфейс `ImageType`, см. `app/media.py`).
- **Способы доставки** (`DeliveryMethod`) — сразу заведены все рассматриваемые
  варианты: самовывоз, СДЭК (курьер и ПВЗ), Boxberry (курьер и ПВЗ), Почта России,
  свой курьер. Каждый включается/выключается и редактируется в админке.
  Стоимость `calculated`-методов пока фиксированная (заглушка до подключения
  API служб — см. TODO в `app/routers/orders.py`).
- **Заказы** (`Order`, `OrderItem`) — создание, список позиций, статус
  (`new → paid → assembled → shipped → delivered`, либо `cancelled` с причиной
  в `cancel_reason`), трек-номер — редактируются в админке на вкладке «Заказы».
- **История статусов заказа** (`OrderStatusHistory`) — каждый переход статуса
  пишется отдельной записью: кто изменил (`changed_by` — логин редактора или
  `system` при автопереходе, например при оплате) и когда. Общая точка записи
  — `app/order_history.py`, используется и в `routers/orders.py`, и в
  `app/admin.py`. Смотреть в админке («История статусов заказов») или через
  `GET /orders/{id}/history`.
- **Клиенты** (`Customer`) — заводятся автоматически по `telegram_id` при первом
  заказе (в `/docs` можно тестировать и без него — гостевой заказ). Хранят
  реферальный код, кто кого привёл, и бонусный баланс.
- **Профиль и «Мои заказы»** (`routers/customers.py`, ТЗ-3 п.2-3 в
  [docs/TZ-02-bot-i-miniapp.md](../docs/TZ-02-bot-i-miniapp.md)) —
  `GET /customers/{telegram_id}` (read-only, 404 если клиента ещё нет —
  новый не заводит, в отличие от `get_or_create_customer`) и
  `GET /customers/{telegram_id}/orders`. Оба под той же проверкой initData +
  сверкой пути, что и адресная книга. `telegram_id` в `POST /orders/` больше
  не принимается в теле — только из проверенного `initData` (ТЗ-0/ТЗ-3 п.4).
- **Проверка владения заказом** (`routers/orders.py`, ТЗ-А в
  [docs/TZ-03-zakryt-dyru-i-miniapp.md](../docs/TZ-03-zakryt-dyru-i-miniapp.md)) —
  `GET /orders/{id}`, `GET /orders/{id}/history` и `POST /orders/{id}/pay`
  раньше принимали `order_id` без проверки initData вообще — чужой заказ
  можно было прочитать или даже «оплатить», просто зная/подобрав его id.
  Теперь все три требуют `X-Telegram-Init-Data` и отдают 404, если заказ не
  найден или принадлежит другому `telegram_id`. Гостевые заказы
  (`customer_id is None`, оформленные через `/docs`) через API теперь не
  читаются вовсе — только в `/admin`.
- **Адресная книга** (`Address`) — клиент сохраняет адрес один раз и
  переиспользует в следующих заказах/подписках (`Order.address_id`,
  `Subscription.address_id`) вместо ввода заново каждый раз. CRUD —
  `/customers/{telegram_id}/addresses`, редактируется и в админке.
- **Склад-заглушка** (`StockMovement`) — на одну физическую точку (офис
  редакции), без учёта нескольких мест хранения. Каждое изменение
  `Product.stock` пишется отдельной строкой: списание при оплате заказа,
  возврат при отмене уже оплаченного, приход/коррекция — когда редактор
  правит остаток в форме товара (разницу считает и логирует само
  `ProductAdmin`, отдельного экрана «приёмка» нет). Резерва остатка на
  момент создания заказа нет — только проверка; см. TODO в
  `routers/orders.py:create_order`. Смотреть в админке («Склад — журнал»)
  или `GET /products/{id}/stock-history`.
- **Отчёт по выручке** (`app/analytics.py`, вкладка «Отчёт по выручке» в
  `/admin`) — считается на лету поверх `Order`/`OrderItem`: выручка,
  количество оплаченных заказов и средний чек за период (фильтр по датам,
  группировка по дням/месяцам), плюс разбивка продаж по товарам. Выручка =
  `Order.total` по заказам с `payment_status == PAID` и `status != CANCELLED`
  (оплаченный и затем отменённый заказ в отчёт не попадает). Отдельной
  таблицы под отчёт нет — не на чем рассинхронизироваться с заказами.
- **Подписки** (`Subscription`) — модель есть, автопродление и списания по
  расписанию — ещё не реализованы (этап 05 дорожной карты).
- **Оплата** (`app/payments.py`) — `StubPaymentProvider`: сразу подтверждает
  оплату без реального списания денег. Точка замены на ЮKassa, когда будет
  готов договор — интерфейс `PaymentProvider.charge()` не меняется. Каждая
  попытка оплаты пишется в `PaymentTransaction` — аудиторский след для сверки.
- **Реферальная программа (MVP)** (`app/customers.py`) — при первой успешной
  оплате приглашённого клиента и пригласивший, и приглашённый получают по 200 ₽
  на бонусный баланс (`BonusTransaction`). Суммы — константы, вынести в
  настройки админки — при необходимости на этапе 05.
- **Персональные аккаунты редакторов** (`AdminUser`, `app/auth.py`,
  `app/security.py`) — раньше был один общий логин на всю редакцию из
  `ADMIN_USERNAME`/`ADMIN_PASSWORD` (.env). Теперь это только бутстрап первой
  записи при пустой таблице (`app/seed.py:ensure_default_admin`) — новых
  редакторов заводить через саму панель, вкладка «Редакторы». У каждого свой
  логин и пароль (хеш — `pbkdf2_sha256`, без внешних зависимостей), поэтому в
  истории статусов заказа видно, кто именно менял статус. Пароль при создании
  редактора можно не указывать — сгенерируется случайный и покажется один раз
  сразу после сохранения (не хранится и не показывается повторно).

## Запуск (Windows / PowerShell)

Важно: в этом окружении алиас `python` в PowerShell указывает на заглушку
Microsoft Store и не создаёт venv молча завершаясь без ошибки — используйте
launcher `py`.

```powershell
cd backend
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env    # один раз — задаёт логин админки и секрет сессии
.\.venv\Scripts\python.exe -m alembic upgrade head   # создаёт схему БД
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

- API и Swagger-документация: http://127.0.0.1:8000/docs
- Админ-панель редакции: http://127.0.0.1:8000/admin (первый вход — логином
  из `.env`: по умолчанию `admin` / `chtivo-admin`, это только бутстрап,
  обязательно сменить пароль или завести отдельного редактора перед реальным
  сервером — вкладка «Редакторы»)

Для локальной разработки нужен Postgres — без `DATABASE_URL` в `.env`
используется локальный SQLite-файл `chtivo_shop.db`, но это работает только
для самой первой миграции: начиная со второй `alembic upgrade head` падает
на SQLite (`NotImplementedError` — см. комментарий в `app/database.py`).
Быстрый старт без установки сервера — Supabase (бесплатный tier),
см. раздел ниже. При старте приложение наполняет пустую базу способами
доставки и парой тестовых товаров (`app/seed.py`) — но саму схему таблиц
создают и меняют **миграции Alembic**, а не приложение при старте.

### Смена базы данных (например, на Supabase)

1. В `.env` — `DATABASE_URL=postgresql+psycopg2://...` (строка подключения
   из Supabase: Project Settings → Database → Connection string → URI).
2. `alembic upgrade head` — создаст все таблицы на новой базе.
3. Перезапустить `uvicorn` — при старте наполнит пустые справочники (доставка,
   тестовые товары).

### Чек-лист переезда с Supabase на Selectel (или другой Postgres-хостинг)

Код моделей/роутеров трогать не нужно — `DATABASE_URL` единственная точка
входа ([app/database.py](app/database.py)), Supabase SDK нигде не
используется, в моделях и миграциях нет Postgres-специфичных типов/расширений
(JSONB, ARRAY, pgvector и т.п.), только стандартные — значит переезд обычно
сводится к трём шагам выше. Но перед этим проверить:

1. **Пароль со спецсимволами/кириллицей.** Если пароль от новой базы содержит
   не-ASCII символы, его нужно percent-encode в `DATABASE_URL`
   (`[uri]::EscapeDataString('пароль')` в PowerShell). При этом
   `alembic/env.py` экранирует `%` как `%%` при передаче URL в
   `config.set_main_option(...)` — `configparser` внутри Alembic иначе
   трактует одиночный `%` как начало интерполяции и падает с
   `ValueError: invalid interpolation syntax`. Это уже сделано в коде и
   сработает для любого хостинга, ничего доп. делать не нужно.
2. **Сеть/файрвол.** Supabase база публична по умолчанию (доступна с любого
   IP через pooler). У Selectel (Managed Postgres или Postgres на отдельной
   VM) обычно нужно **явно разрешить доступ** — добавить IP сервера с
   бэкендом в security group / список разрешённых адресов в панели Selectel,
   иначе `alembic upgrade head` и сам бэкенд не смогут подключиться.
3. **SSL-режим.** Если Selectel требует SSL для подключения (как часто
   требует и Supabase), может понадобиться дописать `?sslmode=require` в
   конец `DATABASE_URL`. Сейчас в коде это никак не ограничено — просто
   иметь в виду, если подключение будет падать с ошибкой SSL.
4. **Перенос реальных данных** (если к моменту переезда в Supabase уже будут
   не только тестовые товары из `app/seed.py`, а настоящие заказы/клиенты) —
   `pg_dump` со старой базы и `pg_restore`/`psql` на новую, до переключения
   `DATABASE_URL` и рестарта `uvicorn`.
5. **Продовые секреты.** Одновременно со сменой базы сменить дефолтные
   `ADMIN_USERNAME`/`ADMIN_PASSWORD`/`ADMIN_SECRET_KEY` в `.env` на реальном
   сервере — сейчас там значения из `.env.example`.

### Если поменяли модель данных (app/models.py)

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "краткое описание изменения"
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Проверить сгенерированный файл в `alembic/versions/` перед применением —
автогенерация не всегда угадывает переименования колонок.

## Тесты

`tests/test_auth_ownership.py` — сценарии из аудита в
`docs/TZ-03-zakryt-dyru-i-miniapp.md` (ТЗ-Д): 401 без `X-Telegram-Init-Data`
и при чужой подписи, 403 на чужой `telegram_id` в пути (`addresses`/
`customers`), 404 на чужой заказ во всех трёх эндпоинтах `routers/orders.py`
(включая `/pay`), гостевые заказы скрыты от API, реферальный бонус
начисляется обеим сторонам после оплаты.

Нужен настоящий Postgres (не SQLite — см. `app/database.py`), отдельная
тестовая БД с накатанными миграциями:

```bash
createdb chtivo_test
pip install pytest httpx
DATABASE_URL=postgresql+psycopg2://<user>@localhost/chtivo_test alembic upgrade head
DATABASE_URL=postgresql+psycopg2://<user>@localhost/chtivo_test \
    BOT_TOKEN=test-token-for-pytest pytest
```

`BOT_TOKEN` для тестов — любой; тесты подписывают `initData` сами (см.
`tests/test_auth_ownership.py:sign_init_data`), реальный токен бота не
нужен. `tests/conftest.py` перед прогоном сбрасывает и пересеивает данные
клиентов/товаров — тестовую БД можно переиспользовать между запусками, она
не для продовых данных.
