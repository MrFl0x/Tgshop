## ТЗ-А · Срочно, до Mini App — закрыть пропуск в ТЗ-0

**Находка (подтверждена живым тестом, не предположение).** ТЗ-0 закрыло
`POST /orders/` и все три эндпоинта `routers/addresses.py` /
`routers/customers.py`. Но в `routers/orders.py` остались **три эндпоинта без
единой проверки initData**:

- `GET /orders/{id}` — отдаёт чужой заказ целиком (имя, контакт, адрес,
  сумма) любому, кто знает/подберёт числовой id.
- `GET /orders/{id}/history` — то же самое для истории статусов.
- `POST /orders/{id}/pay` — **подтверждено живым тестом**: заказ
  оплачивается без единого заголовка авторизации. Любой, кто узнал чужой
  `order_id` (а он последовательный, значит легко угадываемый), может
  «оплатить» чужой заказ — сейчас это просто чужой бонус и бесплатно
  списанный товар со склада заглушкой, но это ровно то место, где будет жить
  реальная логика ЮKassa. Пропуск нужно закрыть **до**, а не после её
  подключения.

**Задачи:**

1. `GET /orders/{id}` и `GET /orders/{id}/history` — добавить
   `telegram_id: str = Depends(get_verified_telegram_id)`, проверять
   `order.customer.telegram_id == telegram_id`. При несовпадении — **404, не
   403** (в отличие от `routers/addresses.py`/`customers.py`, где telegram_id
   и так открыт в самом пути URL — здесь же `order_id` ничего не раскрывает
   сам по себе, и подтверждать чужим запросом «этот заказ существует, но не
   твой» — лишняя информация).
2. `POST /orders/{id}/pay` — та же проверка владения. Отдельно отметить в
   коде (докстрингом): когда подключится ЮKassa, этот эндпоинт по-хорошему
   перестанет быть тем, что вызывает сам клиент — платёж будет подтверждать
   вебхук от ЮKassa (сервер-сервер, с проверкой подписи от них, а не
   initData). Проверка владения нужна именно на переходный период с
   заглушкой, а не как финальная архитектура.
3. Гостевые заказы (без `telegram_id`, оформленные через `/docs` без
   привязки к клиенту — `order.customer_id is None`) — решить: либо закрыть
   такие для чтения полностью (только `/admin`), либо ввести отдельный
   секретный токен заказа для гостевого сценария. Для нынешнего масштаба
   проще первое — гостевой заказ через `/docs` остаётся инструментом
   разработчика, не публичным сценарием.

**Готово, когда:** те же три сценария из аудита (401 без initData / чужой
customer_id → 404 / 403 на addresses и customers) добавляются в постоянный
тестовый скрипт (см. ТЗ-Д ниже) и все проходят для всех эндпоинтов
`routers/orders.py`, не только для `POST /orders/`.

## ТЗ-Б · Мелкая уборка — SQLite как «дефолт для разработки» больше не работает

**Находка.** Миграция `04687c619c59_addresses_admin_users_order_status_.py`
использует `op.create_foreign_key` напрямую. SQLite не поддерживает `ALTER
TABLE ADD CONSTRAINT` без batch-режима Alembic — `alembic upgrade head` на
свежей SQLite падает с `NotImplementedError`. При этом `README.md` всё ещё
описывает SQLite как рабочий вариант по умолчанию.

Раз разработка и так идёт на Supabase (Postgres) — чинить batch-режим ради
пути, которым уже никто не пользуется, не вижу смысла. Предлагаю:

1. `README.md` — убрать формулировку «по умолчанию SQLite», явно написать:
   для локальной разработки нужен Postgres (Supabase free tier — быстрый
   старт, инструкция уже есть в README).
2. `app/database.py` — оставить sqlite-фолбэк как есть (безобидно, ничего не
   ломает), но добавить комментарий, что миграции 2+ на нём не выполнятся.

Если для разработки без интернета/Supabase всё же понадобится offline-режим —
тогда отдельной задачей переписать проблемные миграции в batch-режиме
(`with op.batch_alter_table(...)`). Не делаю сейчас, это не блокирует ничего.

Спецификация не меняется — см. **[docs/TZ-02-bot-i-miniapp.md](TZ-02-bot-i-miniapp.md),

данные — их стоит закрыть в первую очередь той же сессией, что начнёт ТЗ-В,
а не откладывать.

## Необязательно / не блокирует

- **`/orders` в боте** — команда текстом, backend-эндпоинт уже есть
  (`GET /customers/{telegram_id}/orders`). Сам бот прямо признаёт в своём
  README, что этого не хватает — низкий приоритет, делать по желанию.
- **Webhook вместо long polling** — задача деплоя на реальный сервер, не сейчас.
- **ТЗ-Д (рекомендация, не задание): автотесты.** Два реальных бага в этом
  аудите (пропуск проверки на трёх эндпоинтах, сломанные SQLite-миграции)
  нашлись только потому, что я руками поднял сервер и прогнал сценарии.
  Стоит зафиксировать сценарий из аудита как `pytest`-тест
  (`tests/test_auth_ownership.py`) — не как отдельное большое ТЗ, а как
  первый файл теста, который дальше растёт вместе с кодом. Тестовый скрипт
  `_verify_tz.py`, использованный для этого аудита, специально удалён после
  проверки (временный, не для коммита) — но его сценарии 1–7 годятся как
  каркас для этого файла один в один.
