# ТЗ · Этап 02 — бот и Mini App поверх готового backend

Статус на момент написания: backend работает на Supabase (Postgres), схема
управляется миграциями Alembic (head — `bd9f184b7337`), каталог/доставка/
заказы/адреса/клиенты/бонусы/склад/история статусов — реализованы и
проверены end-to-end. Бота и Mini App нет — это ТЗ на них.

Три независимых блока: **ТЗ-0 блокирует публичный доступ**, ТЗ-1 и ТЗ-2 можно
вести параллельно одной командой/сессией, ТЗ-3 — довески к backend, часть из
них нужна до ТЗ-1/ТЗ-2, часть — можно после.

## ТЗ-0 · Защита API (блокирует публичный запуск Mini App)

**Проблема.** `POST /orders/`, `GET/POST/DELETE /customers/{telegram_id}/addresses/`
принимают `telegram_id` как обычный параметр запроса. Ничего не проверяет,
что запрос действительно пришёл от Telegram и что `telegram_id` — это тот, за
кого он себя выдаёт. Сейчас, пока с API работаем только мы через `/docs`, это
не риск. В момент, когда Mini App открывается в браузере любого читателя —
это дыра: чужой telegram_id в теле запроса даёт доступ к чужим адресам,
истории заказов и бонусному балансу.

**Требование.** Telegram передаёт в Mini App подписанную строку `initData`
(её же можно проверить и на стороне бота — там это не нужно, боту Telegram
и так гарантирует `message.from_user.id` через сам Bot API). Backend должен
проверять подпись `initData` по алгоритму Telegram (HMAC-SHA256 на основе
токена бота) и брать `telegram_id` **только из проверенных данных**, не из
тела запроса.

**Задачи:**
1. `app/telegram_auth.py` — функция `verify_init_data(init_data: str, bot_token: str) -> dict`, реализующая проверку подписи ([алгоритм в доке Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)). При невалидной подписи — исключение.
2. FastAPI-зависимость `get_verified_telegram_id`, читающая `initData` из заголовка `X-Telegram-Init-Data`, возвращающая проверенный `telegram_id` или 401.
3. `routers/orders.py` (`POST /orders/`) и `routers/addresses.py` (все три эндпоинта) — убрать `telegram_id` из тела/пути как источник истины, подставлять из зависимости. Путь `/customers/{telegram_id}/addresses` можно оставить как есть в URL для читаемости, но **сверять** его с проверенным telegram_id и отклонять запрос при несовпадении (403).
4. `BOT_TOKEN` — новая переменная в `.env` (нужна и для этого, и для ТЗ-1).

**Не входит в это ТЗ:** rate limiting, защита `/admin` от брутфорса (логин уже
есть — при необходимости вынести отдельным пунктом позже).

**Готово, когда:** запрос с поддельным `X-Telegram-Init-Data` получает 401;
запрос с чужим telegram_id в пути при валидной подписи своего — 403.

## ТЗ-1 · Telegram-бот (aiogram 3.x)

**Цель.** Точка входа в магазин и канал уведомлений о заказе — не витрина
(её показывает Mini App).

**Функционал:**

| Команда/событие | Поведение |
|---|---|
| `/start` | Приветствие + кнопка Mini App (`WebAppInfo`). Если `/start CHT00001` (deep-link с реферальным кодом) — код передаётся в Mini App через `startapp`-параметр, дальше используется как `referral_code` при первом заказе. |
| `/start` (повторный) | Тот же экран — считать реферальный код только при первом визите (клиент уже есть в БД → код игнорировать, см. `get_or_create_customer`, он и так не перезаписывает существующего клиента). |
| Смена статуса заказа | Бот сам пишет клиенту в чат: «Заказ №42 — в пути, трек NNN». Источник события — `OrderStatusHistory` (см. ТЗ-3, пункт 1: нужен хук). |
| `/orders` (опционально, если Mini App не под рукой) | Последние 5 заказов клиента текстом — данные те же, что в ТЗ-3 п. 2 (`GET /customers/{telegram_id}/orders`). |

**Технически:**
- `bot/` — отдельный процесс в этом же репозитории (не внутри `app/`), запускается отдельной командой (`python -m bot.main`), стучится в backend по HTTP (`http://localhost:8000`, конфигурируемо через `.env`) — не импортирует модели `app.models` напрямую. Так бот и API остаются независимыми процессами, которые можно рестартовать/деплоить по отдельности.
- Long polling для старта (webhook — на реальном сервере, отдельная задача при деплое, не сейчас).
- `BOT_TOKEN` — из `.env` (общий с ТЗ-0).

**Готово, когда:** `/start` открывает Mini App; тестовый заказ, переведённый в
админке на статус «В пути», приводит к сообщению в чате у того клиента, чей
`telegram_id` указан в заказе.

## ТЗ-2 · Mini App (React + TypeScript + Telegram WebApp SDK)

**Экраны:**

1. **Каталог** — `GET /products/`. Карточки: обложка (`cover_url`), название,
   цена, остаток (если `stock` не null и небольшой — показать «осталось N»).
2. **Карточка товара** — `GET /products/{id}`, количество, «в корзину».
3. **Корзина** — локальное состояние (не хранится на backend, пока не оформлен заказ).
4. **Оформление заказа:**
   - Способ доставки — `GET /delivery-methods/`.
   - Адрес — если у способа `requires_address: true`: список сохранённых
     (`GET /customers/{telegram_id}/addresses/`) с возможностью выбрать
     (`address_id`) или ввести новый (`delivery_address`); опция сохранить
     новый адрес в книгу — отдельным вызовом `POST .../addresses/`, не через заказ.
   - Отправка — `POST /orders/`, поле `telegram_id` в теле **не отправлять**
     (см. ТЗ-0 — backend возьмёт его из `initData`, поле фактически
     устаревает вместе с вводом ТЗ-0 и должно быть удалено из `OrderCreateIn`).
   - Оплата — `POST /orders/{id}/pay` (пока заглушка — вызывается сразу же,
     без внешнего платёжного окна; когда подключится ЮKassa, здесь появится
     редирект на форму оплаты — интерфейс вызова с фронтенда не изменится).
5. **Статус заказа** — `GET /orders/{id}` + `GET /orders/{id}/history` (таймлайн статусов).
6. **Профиль** — бонусный баланс и реферальная ссылка (`t.me/<bot>?start=<referral_code>`);
   требует нового эндпоинта — см. ТЗ-3, п. 3.
7. **Мои заказы** — список — требует нового эндпоинта — см. ТЗ-3, п. 2.

**Технически:**
- Инициализация через `@telegram-apps/sdk` или `window.Telegram.WebApp`; при каждом запросе к backend — заголовок `X-Telegram-Init-Data: <initDataRaw>`.
- Цветовая тема — из `Telegram.WebApp.themeParams`, поверх фирменного стайлгайда «Чтиво» (первая содержательная задача дизайна, ещё не решённая — см. открытые вопросы в продуктовом плане).
- CORS — если Mini App хостится не с того же домена, что backend, нужен `CORSMiddleware` в `app/main.py` (сейчас не подключён — добавить перед первым внешним деплоем фронтенда; для локальной разработки через `/docs` не мешало).

**Готово, когда:** реальный тестовый пользователь Telegram проходит путь
каталог → заказ → заглушка оплаты → видит статус — без обращения к `/docs`.

## ТЗ-3 · Довески backend (нужны под ТЗ-1/ТЗ-2, без них клиент неполный)

1. **Хук уведомлений** — при записи в `OrderStatusHistory` (см.
   `app/order_history.py:record_order_status_change`) вызывать колбэк/событие,
   которое бот слушает и шлёт сообщение клиенту. Простой вариант для этого
   масштаба — не очередь (Celery/RQ, это отдельная задача этапа 05), а прямой
   HTTP-вызов из backend в локальный эндпоинт бота (`bot` поднимает свой
   маленький HTTP-приёмник) либо бот сам поллит `/orders/{id}/history` — выбрать
   один вариант при реализации, не оба.
2. **`GET /customers/{telegram_id}/orders`** — список заказов клиента
   (`OrderOut[]`, без чужих заказов). Нужен для экрана «Мои заказы» (ТЗ-2 п. 7)
   и команды `/orders` (ТЗ-1).
3. **`GET /customers/{telegram_id}`** — профиль: `full_name`, `contact`,
   `referral_code`, `bonus_balance`. Нужен для экрана «Профиль» (ТЗ-2 п. 6).
   Аналог уже есть в `get_or_create_customer` — здесь просто read-only обёртка,
   без создания нового клиента, если его ещё нет (404, если не найден).
4. **Убрать `telegram_id` из `OrderCreateIn`** (`app/schemas.py`) — после
   ТЗ-0 это поле избыточно и вводит в заблуждение, откуда на самом деле берётся
   telegram_id.

Все три — небольшие, укладываются в 1–2 дня, логично сделать в начале ТЗ-1/ТЗ-2,
а не в конце.

**Статус: пункты 2–4 сделаны.** `routers/customers.py` — `GET /customers/{telegram_id}`
(профиль, 404 если клиента ещё нет) и `GET /customers/{telegram_id}/orders`
(список, `[]` если клиента нет), оба под тем же `get_verified_telegram_id` +
сверкой пути, что и `routers/addresses.py`. `telegram_id` убран из
`OrderCreateIn` (`app/schemas.py`) — поля больше нет физически, не просто
игнорируется. Проверено end-to-end с временно подставленным тестовым
`BOT_TOKEN` (локально, не сохранён): заказ без `telegram_id` в теле → профиль
→ список заказов; 401 без заголовка; 403 при чужом `telegram_id` в пути.

## Не входит в этот этап (сознательно отложено)

- **Реальная доставка** (СДЭК/Boxberry API вместо `fixed_cost`-заглушки) —
  независимый трек, TODO уже в `app/routers/orders.py`. Не блокирует бота/Mini App.
- **Реальная оплата** (ЮKassa вместо `StubPaymentProvider`) — ждёт юрлица
  редакции, интерфейс `PaymentProvider.charge()` в `app/payments.py` менять не придётся.
- **Автопродление подписки** — модель `Subscription` есть, движка списаний
  по расписанию нет (нужен планировщик — Celery/RQ, этап 05 дорожной карты).
- **Переезд Supabase → Selectel** — обязателен до первого заказа с реальными
  персональными данными (152-ФЗ), не связан с ботом/Mini App технически.
- **Тесты (pytest)** — не блокирует этот этап, но по-хорошему завести до того,
  как логика (реферальные бонусы, история статусов, остатки) обрастёт ещё
  большим числом взаимосвязей — рекомендация, не требование.
